## Embedding lesson pages in Schoology

**Reverted to a plain `<iframe>` (Sep 2026).** The earlier approach — a `<script>`-based
fetch-and-inject into a shadow root, avoiding an iframe entirely — worked when tested locally
(see git history for that writeup) but this Schoology instance rejects `<script>` tags pasted
into Page HTML, same as the caveat below flagged as the main risk. Since the script never runs,
there's nothing to fall back to but the iframe.

### Schoology-side snippet

Every non-unit page's footer has a **📋 Copy Embed for Schoology** button that copies this for
the exact page you're on. In the Page material's editor, switch to the HTML/source view and
paste it:

```html
<iframe src="https://digcom.cambron.cc/foundations/fdd1/1_1.html" style="width: 100%; height: 85vh; min-height: 500px; border: 1px solid #ccc; border-radius: 6px;" loading="lazy"></iframe>
```

It still re-fetches the live page on every load — edits pushed to this site show up in Schoology
the next time a student opens the page, nothing to re-paste. What it doesn't get from the old
approach: style isolation (the iframe's content uses its own stylesheet inside the frame
boundary, same as any iframe — this was never actually a problem specific to the injection
approach) and a custom failure state if the page is unreachable (an iframe just shows its own
browser error, not a "open it directly" link).

**The `height` is 85% of the Schoology window, not the page's length (Sep 2026).** The iframe is
`height: 85vh; min-height: 500px`: `vh` is measured against the Schoology page's own browser
window, so the frame fills most of the screen on anything from a Chromebook (~540px) to a
windowed 24" iMac (~900px), and students scroll inside it. The full site layout loads inside the
frame, so the sidebar navigation stays usable wherever the frame is at least 800px wide (below
that, just-the-docs collapses it to a ☰ menu button, which is what happens on most Chromebooks).
Tested in Schoology on FDD 2.1 before rolling out — Schoology keeps the `vh` value.

This replaced an earlier approach that sized each iframe to its page's full length, from a
`_data/embed_heights.json` file generated by a Playwright script. That never fit well: the first
version measured pages over `file://` without their stylesheets and recorded heights 2–3× too
tall, and even measured correctly, the right height depends on the frame's width (just-the-docs'
sidebar appearing at exactly 800px changes a page's height by ~700px). Both the script and the
data file are gone; there's nothing to regenerate after content edits.

### Unit overview pages get a different, static-HTML embed (Sep 2026)

A unit's `index.md` (Introduction / intro video / Learning Outcomes / Calendar of Events) gets a
**📋 Copy Static Embed for Schoology** button instead of the iframe above. Reasoning: a unit page
is the one page a teacher is likely to want live inside Schoology itself (not just linked out to)
even if this site's iframe embedding were ever blocked by a Schoology CSP/domain-allowlist
change — see the Caveats below. Copying it as plain, self-contained, inline-styled HTML (no
iframe, no dependency on this site's stylesheet) means it always renders once pasted into a
Schoology Page's HTML editor, regardless of whether framing `digcom.cambron.cc` itself ever stops
working there.

This is built by `_includes/unit-static-embed.html`, included automatically by
`footer_custom.html` for any page that structurally looks like a unit overview (has children, and
its content has `## Introduction` / `## Learning Outcomes` / `## Calendar of Events for This
Unit` headings) — not a front-matter flag, so any future unit page qualifies with zero setup. It
parses the Introduction and Learning Outcomes straight out of the page's own markdown (through
Jekyll's `markdownify` filter) and rebuilds the calendar table from `site.data.calendar`, so
editing a unit's copy or the calendar data is picked up on the very next `jekyll build` — nothing
to regenerate by hand, unlike the iframe heights above.

### Caveats

- **If iframes are "unreliable" here for a reason other than script-blocking** (e.g. the
  Schoology instance's own CSP or an admin-configured domain allowlist for framed content), an
  iframe pointed at `digcom.cambron.cc` may still not render. Test with one real Page first.
- **Schoology's mobile app** has historically had rougher iframe support than its desktop/browser
  view — verify there too before depending on this for mobile-heavy classes.
- No fixed height is right for every lesson — long lessons will scroll inside the frame, short
  ones will leave empty space below. There's no reliable cross-origin auto-resize without the
  embedded page's own JS cooperating (postMessage), which runs into the same script-rejection
  problem this reverted away from.
